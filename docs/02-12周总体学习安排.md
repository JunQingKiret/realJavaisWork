# 12 周总体学习安排

> **历史对照稿，不是当前推荐执行计划。** 本稿 v0.1 假定学生已能独立做完整 V0；教师后续反馈不支持这个前提。2026-10-12 的新路线见《基础优先总体学习安排》：推荐讨论 16 周，或采用该文中的 12 周降载备选。不要将本稿全部任务直接发给当前学生，也不要把新第一周和本稿第 2 周机械拼接。

> 教师讨论稿 v0.1｜2026-10-12。人数 3–4，学生正在学习 Java 8；每人每周暂按 5–6 小时课外总投入。第 1 周诊断后决定是否降载。

## 1. 课程定位

**主线：先把业务做出来，再解释为什么要重构、持久化、Web 化和引入框架。**

框架线路暂按 Java 21 + Boot 4.1.x + MyBatis Starter 4.0.x；具体补丁和可复现模板尚待教师验证。若必须用已有 Boot 3 教材，对照备选及已结束 OSS 支持的说明见特性与资料文档。不是给学生再加一轮 Boot 3→4 迁移。

不按 Java 版本史逐章讲授，不要求每个底层技术都独立做成框架。每次迁移保留业务验收场景，让学生看到“实现方式变了，规则没有凭空改变”。

最终作品是本地运行的教学 API，包含虚构商品、卖家昵称和成交记录；不是带真实用户认证和支付的交易平台。不以做出完整前端作为结业前提。

## 2. 每周时间模型

| 活动 | 每人投入 | 作用 |
|---|---:|---|
| 指导 A | 75 分钟 | 演示痛点、讲必要概念、启动本周任务 |
| 自主练习 A | 90 分钟 | 独立尝试、提交问题与初版 |
| 指导 B | 75 分钟 | 针对卡点讲解、结对排查、明确验收 |
| 自主练习 B | 60–90 分钟 | 完成最小任务、测试、更新说明 |
| 小组验收 | 30 分钟 | 每人解释或修改一小段代码 |
| **总计** | **5.5–6 小时** | 包含填写记录与互审，不再追加日常站会 |

第一周自主练习额外拆成三个短段，但总量仍在此范围。后续每周只安排两次短文字进度反馈。考试周优先去掉选做和新技术，不要求学生靠加班追平。

## 3. 各版本的最小产物

| 版本 | 必做产物 | “痛点 → 技术”的解释 | 刻意不做 |
|---|---|---|---|
| V0 | 内存控制台：发布、列表、搜索、退出 | 先验证需求与 Java 基础 | 用户系统、数据库、数组/集合两套重复实现 |
| V1 | Product / ProductService，职责拆分；手工传入依赖 | 单类逻辑混杂 → 封装与职责分离 | 为每个类都制造接口、完整设计模式 |
| V2 | Repository 接口、内存实现、异常边界 | 替换存储和表达业务错误 → 接口/集合/异常 | 自制容器；为展示 Stream 牺牲可读性 |
| V3 | Maven 工程、测试、SQL、JDBC 持久化 | 重启丢数据/手工依赖 → 工程化和 DAO | 大表设计、ORM 原理大全 |
| V4 | 教师提供 HTTP 适配骨架，学生接入既有 Service；JSON API | 控制台单入口 → 请求/响应与 API | 从头写网络服务器、完整客户端 |
| V5 | 实验分支中显式注册两个带注解的方法并调用 | 路由分发重复 → 运行时元数据 | 完整 MVC、自动扫描、参数绑定框架 |
| V6 | Spring Boot 分层 API、MyBatis、校验、错误响应、测试与打包 | 手工装配/基础设施重复 → 框架与自动配置 | 真实支付、认证体系、公网发布 |

V5 是短实验，不必并入主线；完成后对比“我们写过的哪一小段机制在 Spring 中由框架负责”。

## 4. 逐周计划

| 周 | 版本与驱动问题 | 必讲/必做 | 每名学生验收 | 小组产物 | 选做/可删项 |
|---|---|---|---|---|---|
| 1 | V0：能否独立完成输入到结果？ | 基础诊断；Java 8/21 环境隔离；菜单、发布、列表、搜索；Git 本地提交 | 独立运行、解释数据流、现场小改；非法输入可恢复 | 每人一份 V0 和测试记录 | 文本块/箭头 switch 改写；不要求 var |
| 2 | V1：为什么 main 不该承担所有职责？ | 普通类、封装、ProductService；手工构造和传入依赖；保持功能不退化 | 解释 Product 与 Service 职责；修改一个商品规则 | 结对审查，选定团队主仓库基础；保留个人版本 | Record 商品摘要；实体与 DTO 对比演示 |
| 3 | V2：如果将来换成数据库怎么办？ | ArrayList/泛型按需深化；Repository 接口与内存实现；异常在边界转换提示 | 替换一个内存实现或补一个错误场景；解释接口意义 | 发布/搜索依赖 Repository；首次小 PR | Lambda/Stream 复习；sealed/有序集合识读 |
| 4 | V2→V3：工程如何稳定复现？ | Maven 标准目录、依赖与构建；引入 JUnit；写两项业务测试；SQL 表与增查改；准备数据库 | 本机一条构建流程通过；至少写/解释一项测试及参数化查询思路 | 工程模板、建表脚本、第一批测试；补前期欠账 | 更复杂 SQL、覆盖率工具、额外查询 |
| 5 | V3：数据如何在重启后保留？ | JDBC Repository、PreparedStatement、资源关闭；标记已售 + 成交记录事务 | 查询重启仍在；解释两步修改的原子性；演示人为失败回滚 | JDBC 版通过发布/查询/成交验收 | 并发压力实验；复杂关系查询 |
| 6 | V4：一次 HTTP 请求与程序方法调用有何不同？ | HTTP 方法/状态/JSON；教师提供轻量 HTTP 骨架；GET 列表、POST 发布；复用 Service | 能用 API 工具发送请求，并定位请求到响应的路径 | API 文档初稿；内存或 JDBC 后端均可先跑通 | 虚拟线程演示；不承诺原生演示服务的并发安全 |
| 7 | V4→V5：每条路由都手写分发有什么重复？ | 完成搜索/详情与错误响应；固定迁移验收场景；60–90 分钟注解路由实验 | 读出两个注解注册信息，解释 Method.invoke；用用例确认 API 行为 | V4 基线；单独 V5 实验分支，不开发完整框架 | 动态代理；Record Patterns；switch 模式匹配 |
| 8 | V6：谁来创建和连接依赖对象？ | Boot 启动；Controller/Service/Repository；构造器注入；保留 JDBC 实现先迁移；自动配置的证据 | 画出手工 new 与 Spring 装配对照；解释一个 Bean 和依赖 | Boot 版发布/列表/搜索；原 V4 请求场景回归 | 自动配置源码深挖；组件扫描原理大全 |
| 9 | V6：框架如何帮助表达 API 契约？ | Spring MVC；请求/响应 DTO、Validation、全局异常；补齐编辑/下架；统一搜索参数；分页可选 | 新增一个校验规则并解释错误响应；验证两项边界 | 发布/详情/搜索/编辑/下架契约稳定；无敏感调试信息返回 | 分页并限制大小；AOP 日志演示；单页展示 |
| 10 | V6：持久化代码还能简化多少？ | MyBatis Mapper；替换 JDBC 访问实现，不同时重写业务；Spring 事务；验证重复成交被拒绝 | 对照 SQL、Mapper、Service；人为失败时回滚；解释事务入口 | MyBatis 版本回归通过；成交流程与事务用例 | AOP 由学生实现；复杂映射和多表查询 |
| 11 | V6：换一台机器为什么容易跑不起来？ | 配置/Profile；本地密钥不提交；可执行包；Service 单元测试与至少一项 API 集成测试 | 按 README 在干净目录重建/运行；解释配置来源 | 交付候选版、示例配置、建表脚本、测试报告 | 公网部署、Docker、负载压测 |
| 12 | V6：我们能解释并维护自己的作品吗？ | 不再加技术；查漏补缺、演示、个人现场修改、复盘 | 每人独立完成一项小改动并补验收；讲清一次完整请求链路 | 最终发布标签、README、版本对照、复盘 | 无新增范围；有余力才润色展示 |

### 第 5 / 10 周事务案例的统一契约

- 两张最小表：商品表和成交记录表；金额使用一致的精确表示，不用浮点数直接存交易金额。
- 商品状态：在售/已售/下架；买卖身份只用虚构昵称，不加入登录。
- 成交时，条件更新“该商品仍在售”的状态，再写入成交记录；未更新到一行就拒绝。
- 两步属于同一事务；教师提供的故障点使第二步失败，验证第一步也回滚。
- 成交记录约束每件商品至多一条；参数通过 PreparedStatement/MyBatis 参数绑定，不拼接用户输入。
- 原生 JDBC 的连接、提交/回滚由学生看到；Spring 中再对照由事务机制负责的部分。
- Spring 事务示例通过外部调用进入受管理 Service 的事务方法，不以同类内部调用作为生效示范。

这些是受控本地实验，不承诺生产级并发、权限或支付安全。

## 5. 3–4 人协作方式

### 防止“一个人做，其他人看”

- 第一周所有人独立完成全部最小功能，不按“甲写菜单、乙写搜索”拆开。
- 第 2 周结对互审，用各自代码讲优缺点；第 3 周起维护一份小组主仓库。
- 团队任务拆成可独立验收的小改动，不把某一层长期交给固定学生。
- 每周每人必须有：一项自己的可解释改动、一条验证记录、一次口述/现场修改。
- 合并他人代码前至少由另一人复述改动目的和风险。

### 轮换角色

| 角色 | 本周职责 |
|---|---|
| 业务实现 | 实现一项明确规则或功能 |
| 测试与审查 | 提供正常/异常用例，检查对应改动 |
| 集成与发布 | 处理小范围合并，确认主线可运行，更新版本说明 |
| 文档/API（4 人时） | 更新使用方式、接口示例，验证说明与实现一致 |

3 人时文档由集成角色兼任。角色只是主要责任，每人仍要写代码和参与测试；每周轮换。

## 6. AI 使用规则：阶段 + 能力门槛

| 阶段 | 允许 | 不允许/先决条件 | 验证要求 |
|---|---|---|---|
| 第 1–2 周 | 概念解释、报错解释、提问提示；教师提供脚手架 | 不生成要提交的功能代码；不把完整任务交给 AI | 自己写代码；说清建议是否采纳；未使用就记录未使用 |
| 第 3–5 周 | 先独立实现，再对照 AI 方案；每周选一个 10–20 分钟小任务做“先写后比” | 不要求整个项目重写两遍；需先能独立完成菜单/集合基本任务 | 保留自己的初稿，比较差异，运行同一组用例 |
| 第 6–7 周 | Ask → Code → Review；一次辅助一个小改动 | 不让 AI 一次生成整个 HTTP 服务或迷你框架 | 先写 API 约束，再看 diff，再跑正常与错误场景 |
| 第 8–11 周 | 经个人解释检查后允许 Agent 辅助多文件改动 | 一次一个任务；不允许未经阅读就合并；不提交账号、密钥、真实身份数据 | 先列验收条件，审查修改范围，运行测试，现场解释 |
| 第 12 周 | 帮助整理复盘材料 | 个人现场修改环节不使用 AI | 以独立解释、修改和验证作为个人能力证据 |

能力门槛不足时减少 AI 改码范围，不扣除求助机会。教师也应区分学生原创、提供的脚手架和 AI 建议，不用“代码很多”评价能力。

## 7. Git 教学按真实需求推进

- 第 1 周：本地初始化、暂存、提交、历史、改动差异；先讲三种提交前缀即可。
- 第 2 周：个人重构分支、合并、认识冲突；不用人为复杂冲突练习占满课时。
- 第 3 周：远程仓库、PR/合并请求、审查；账号困难者先本地展示，不挡业务学习。
- 第 4–5 周：忽略构建产物、敏感配置；测试与 README 随功能更新。
- 第 6–7 周：小任务分支；教师示范撤销未提交改动与用新提交撤销旧改动的区别，不让学生对共享历史随意强推。
- 第 8–12 周：迁移分支对照、里程碑 tag、最终发布说明。

## 8. 评价与关卡

### 阶段关卡

| 时间 | 过关条件 | 未过关处理 |
|---|---|---|
| 第 1 周末 | 独立运行 V0；输入错误可恢复；能解释并小改 | 补菜单/方法/输入；删除新语法选做，不让强者包办 |
| 第 3 周末 | 能说明 Service、Repository、接口与异常的职责 | 第 4 周用预留时间补重构；不追加 sealed/Stream 技巧 |
| 第 5 周末 | 数据重启仍在；资源关闭正确；事务故障回滚 | 用教师最小数据库脚本；补参数化 SQL 与事务，删复杂查询 |
| 第 7 周末 | 至少发布/查询 API 正常；错误响应可验证 | 取消 V5 学生实现，改为教师演示；不推迟整个 Boot 阶段 |
| 第 10 周末 | Boot + MyBatis 保持业务用例；校验、异常、事务可说明 | 用第 11 周前半段补齐；不加 AOP/前端/部署 |
| 第 12 周 | 可按说明复现；每人完成现场修改 | 按未完成项给出补交清单，不用小组演示掩盖个人缺口 |

### 总评价建议

- **个人 70%**：解释与现场修改 25、个人功能/验证 25、问题解决和 AI 判断 10、提交与学习记录 10。
- **小组 30%**：功能与错误场景 15、可复现交付 10、审查和职责轮换 5。
- 第一周按独立任务评价，不计团队分；不要用提交次数、代码行数和 AI 使用量作为主要分数。

### 结业最低标准

1. API 支持发布、列表/搜索、详情、编辑/下架和受控的“成交”流程；无登录/支付。
2. 数据持久化；无非法价格、空名称或重复成交的悄然成功。
3. 至少 4 项关键 Service 自动化测试和 1 项 API 集成测试；具体数量可按课时调整，重点看是否覆盖关键规则。
4. JDBC 与 Spring 阶段各有一份事务回滚的可复现证据。
5. README 说明 JDK、框架具体版本、数据库准备、配置、运行与测试方法；他人可以照说明跑起来。
6. 每人回答请求链路/DI/SQL/事务/新特性中的问题，并完成一项不依赖 AI 的小修改。

## 9. 低课时与进度落后时的处理

- 每周只能投入 3–4 小时：不机械压缩全部内容；改为 14–16 周，或取消学生手写 V5、代理、AOP、虚拟线程和前端。
- 前两周发现基础明显不足：先补集合、异常和方法拆分，框架迁移目标保持，但不强行赶完整 12 周。
- 全组基础强：减少重复 Java 8 讲解，把时间给测试、API 契约和数据库规则；不是增加技术清单。
- 数据库环境持续卡住：先用教师已验证的本地方案和脚本排查；API 阶段可先使用内存实现，随后切回数据库。
- 版本依赖不一致：全组回到教师验证的版本组合，不在课堂临时解决大版本迁移。

## 10. 教师开课前的准备清单

- [ ] 确认学生校内 JDK 要求和正在学习的章节。
- [ ] 准备 5 分钟最终 API 演示；若尚无最终项目，用静态请求/响应示例，不要求老师先完成全部系统。
- [ ] 准备第一周最小 Product 类与价格转换辅助代码（只在需要时发放）。
- [ ] 第 4 周前验证 Maven 模板、JUnit 测试和数据库建表脚本。
- [ ] 第 6 周前验证轻量 HTTP 骨架；只允许教学使用，不把它包装成生产服务。
- [ ] 第 8 周前锁定 Boot 4.1.x/MyBatis Starter 4.0.x 的具体补丁版本并验证启动、连接、测试和打包。
- [ ] 给每周任务设“必做、选做、到点停止”，留出考试周和环境排查缓冲。

## 11. 下一次共备需要确认

学生当前章节、每周可用时间，以及“原理理解/作品完成”的侧重。确认后才把相对的 D1–D7 换成实际日期，并最终确定版本、评分方式和脚手架范围。
