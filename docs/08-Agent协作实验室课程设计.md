# Agent 协作实验室：先体验协作、再发现局限、最后共同创作

> 讨论稿 v0.1｜2026-10-16  
> 目标：第一节课不直接教 Agent API 或枯燥基础语法，而是让学生通过一个可视化软件经历“Agent 生成—发现问题—调用工具—人工验证—共同交付”的完整过程，再从真实问题中引出 Java 知识。

## 1. 课程主角不是仓库查询器，而是“Agent 协作实验室”

建议教师准备一个简单的协作软件，暂名：

> **Agent Collaboration Lab / Agent 协作实验室**

第一周给它一个具体项目空间：

> **103 仓库数字导览项目**

学生和 Agent 的共同任务不是单纯查库存，而是制作一个有视觉成果的内容，例如：

- 103 仓库一页式数字导览；
- 本周库存简报；
- 新成员入库操作指南；
- 常见物品查找 FAQ；
- 低库存预警说明页；
- 仓库开放日介绍页面。

最终课堂上能直接看到一个网页或报告，而 Java 工具在背后负责提供真实数据和验证结果。

## 2. 软件界面建议

软件不应只有聊天框，至少需要五个区域：

```text
┌──────────────────────────────────────────────────────────────┐
│ 项目目标：为新成员制作 103 仓库数字导览                    │
│ 受众：第一次进入仓库的学生   限制：不得虚构物品和位置      │
├───────────────────┬──────────────────────┬───────────────────┤
│ 与 Agent 对话      │ 作品实时预览          │ 证据与验证         │
│                   │                      │                   │
│ 用户需求           │ 标题、卡片、表格、FAQ │ 调用了哪些工具     │
│ Agent 计划          │                      │ 使用了哪些数据     │
│ 修改意见           │                      │ 哪些内容未验证     │
├───────────────────┴──────────────────────┴───────────────────┤
│ 执行轨迹：计划 → search_inventory → get_safety_rules → 输出 │
├──────────────────────────────────────────────────────────────┤
│ [Agent 直接生成] [允许使用工具] [运行事实核验] [导出作品]  │
└──────────────────────────────────────────────────────────────┘
```

三个最关键的按钮：

1. **Agent 直接生成**：让学生看到仅凭语言模型生成的结果；
2. **允许使用工具**：让 Agent 读取 Java 工具提供的真实数据；
3. **运行事实核验**：检查内容中的数量、位置、状态和规则是否有证据。

同一个作品经过三个阶段不断变化，学生能直观看到“会写”和“写得对”不是一回事。

## 3. 第一节课的完整剧情

### 阶段一：先展示 Agent 的惊艳能力

教师输入一个很宽泛的需求：

```text
请为第一次进入 103 仓库的学生，制作一份漂亮、容易阅读的数字导览。
```

Agent 很快生成：

- 欢迎标题；
- 仓库介绍；
- 热门物品；
- 分区说明；
- 安全提示；
- FAQ；
- 一页式网页预览。

学生首先产生“它真的能做出来”的直观体验。

### 阶段二：让学生找出看起来合理但实际错误的内容

教师不要立刻评价，而是让学生寻找问题。例如 Agent 可能写出：

- “仓库共有 120 类物品”，但没有数据来源；
- “每天 8:00–22:00 开放”，实际从未提供开放时间；
- “灭火器位于 D 区”，仓库数据中不存在这条信息；
- 把低库存物品写成“库存充足”；
- 写出了漂亮但无法执行的操作流程。

此时软件右侧显示：

```text
已验证事实：2
缺少证据：5
与数据冲突：2
高风险操作：1
```

教师总结：

> Agent 的语言可能非常流畅，但流畅不代表事实正确。

### 阶段三：打开工具调用轨迹

允许 Agent 使用 Java 工具：

- `get_inventory_summary()`；
- `search_inventory(keyword)`；
- `get_item_location(itemId)`；
- `list_low_stock(threshold)`；
- `get_safety_rules()`。

学生看到：

```text
Agent 计划：先获取仓库概况，再获取低库存和安全规则。

工具调用：get_inventory_summary
工具结果：物品种类 9，库存总数 187

工具调用：list_low_stock
参数：threshold=5
工具结果：键盘 2，无线鼠标 1
```

然后作品中的虚构数字被真实数据替换。

### 阶段四：继续暴露 Agent 的局限

即使有工具，也不代表一定正确。可以人为安排以下故障：

1. Java 搜索工具只返回第一条数据；
2. 低库存判断错误地使用 `<` 而不是 `<=`；
3. 某条仓库备注中含有“忽略之前要求”的恶意文本；
4. Agent 使用了旧工具结果，没有重新查询；
5. 工具返回空数组，Agent 却自行补充了答案；
6. Agent 准备修改库存，但没有询问确认。

学生由此理解：

- Agent 可能理解错；
- 工具也可能写错；
- 输入数据可能不可靠；
- Agent 不会自动完成严谨验证；
- 人仍然需要定义目标、检查证据和批准危险操作。

### 阶段五：学生与 Agent 共同完成作品

学生分组或轮换担任：

- **需求负责人**：说明受众、目标和不能虚构的内容；
- **工具开发者**：修复一个 Java 查询或验证工具；
- **事实核验员**：检查每个关键事实的数据来源；
- **内容编辑者**：调整结构、表达和最终展示效果。

3–4 名学生不固定角色，每 15–20 分钟轮换一次。

最终交付不是“Agent 自动生成的网页”，而是：

> 学生定义需求、Java 提供事实、Agent协助组织、人类完成验证的一份数字导览作品。

## 4. 最适合第一周的最终内容

推荐选择：

> **103 仓库新成员数字导览页**

它可以包含：

1. 仓库用途介绍；
2. 区域与位置说明；
3. 常用物品卡片；
4. 当前低库存提示；
5. 安全规则；
6. 常见问题；
7. 数据更新时间和来源说明。

选择它的原因：

- 比控制台程序更有观赏性；
- Agent 擅长帮助组织内容；
- Java 工具可以提供事实数据；
- 很容易加入真假对比；
- 最后可以直接投屏展示；
- 后续可自然演化为 Spring Boot 网站。

## 5. 周日 90 分钟流程

| 时间 | 环节 | 教师操作 | 学生任务 |
|---|---|---|---|
| 8:10–8:16 | Agent 快速创作 | 输入模糊需求，生成一份漂亮导览 | 观察 Agent 做得好的地方 |
| 8:16–8:28 | 找茬挑战 | 不提示错误，开放作品和仓库原始资料 | 找出虚构、冲突、缺证据内容 |
| 8:28–8:36 | 揭开协作结构 | 展示目标、计划、工具调用、作品、验证五层 | 判断问题发生在哪一层 |
| 8:36–8:47 | 启用 Java 工具 | 让 Agent 查询真实库存、位置和规则 | 对比工具前后的作品变化 |
| 8:47–9:00 | 故障实验 | 让错误搜索工具返回不完整结果 | 追踪并修复一处简单逻辑 |
| 9:00–9:12 | 人机协作改稿 | 学生补要求，Agent重新生成，Java提供数据 | 完成一轮需求—生成—修改 |
| 9:12–9:22 | 事实核验 | 运行检查器，查看未验证事实和冲突 | 修复至少一个事实问题 |
| 9:22–9:32 | 内容创作 | 每人负责一个板块或一项工具能力 | 导览页形成个人贡献 |
| 9:32–9:38 | 展示与复盘 | 展示初稿和终稿对比 | 说明 Agent 帮了什么、错了什么 |
| 9:38–9:40 | 离场票 | 发布第一周任务 | 写下下一项要补的能力 |

## 6. 课堂需要明确展示的 Agent 局限

第一节课不要罗列十几个抽象风险，重点让学生亲眼看到五类：

### 6.1 需求不清，结果只能“猜”

输入“做一个好看的仓库介绍”，Agent 不知道：

- 给谁看；
- 展示哪些区域；
- 是否允许显示库存；
- 风格和长度；
- 哪些事实必须来自数据。

引出：需求、约束、验收标准。

### 6.2 语言流畅不等于事实正确

Agent 可以自然地补出不存在的开放时间、物品数量和安全规则。

引出：证据、数据来源和人工核验。

### 6.3 Agent 的能力受工具限制

没有位置查询工具，它就无法可靠回答物品在哪里；工具只返回第一条，它也可能得到不完整结果。

引出：方法、循环、List、返回值和测试。

### 6.4 输入数据错误，Agent也会被带偏

工具或数据源有误时，Agent可能把错误包装成更流畅的答案。

引出：数据校验、异常处理和测试。

### 6.5 Agent不应自动执行危险操作

涉及修改、删除、批量更新时，必须限制工具权限并由人确认。

引出：权限、确认、审计和业务规则。

## 7. 学生第一周实际需要完成什么

不要求从零开发整个协作软件。教师提供软件骨架，学生完成以下四项：

1. 为导览页写出明确的目标、受众和三条约束；
2. 修复或完善一个 Java 工具；
3. 使用 Agent 生成一个内容板块；
4. 对该板块执行事实核验，并说明修改依据。

每人至少提交一项可识别贡献：

- 一个工具修复；
- 一个验证规则；
- 一组真实数据；
- 一个内容板块；
- 一组测试场景。

不能只把 Agent 输出复制到最终作品中。

## 8. Java 知识如何自然出现

| 软件需求 | 被需要的 Java 知识 |
|---|---|
| 保存多件仓库物品 | 类、对象、List |
| 查找包含关键字的物品 | String、循环、if |
| 找出低库存物品 | 比较、筛选、方法 |
| 给 Agent 返回结构化数据 | DTO/Record、JSON |
| 区分“未找到”和“工具失败” | 异常、错误类型 |
| 检查导览中的数字是否真实 | 测试、断言、验证规则 |
| 保存作品和数据 | 文件、JDBC、数据库 |
| 给网页或C#客户端使用 | HTTP、REST、Spring Boot |
| 防止Agent直接删数据 | 接口边界、权限、确认 |

这仍然是在学 Java，只是每个知识点都有一个立即可见的软件用途。

## 9. 软件需要有的四种模式

### 演示模式

教师预设任务、错误和数据，保证课堂剧情稳定。

### 学生模式

学生可以修改需求、运行 Agent、查看工具轨迹和编辑作品。

### 离线模式

没有网络或 API 时，使用 FakeAgent 按预设轨迹模拟 Agent 调用，Java工具仍然真实执行。

### 回放模式

保存每次：

- 用户需求；
- Agent计划；
- 工具调用；
- 工具结果；
- 初稿；
- 人工修改；
- 验证结果。

周汇报直接用时间线回放，不需要额外剪视频。

## 10. 第一周验收方式

每人用 90 秒回答：

1. 我们给 Agent 的任务是什么；
2. Agent 的初稿有什么问题；
3. 它调用了什么工具；
4. 我修改了哪段 Java 或哪条验证规则；
5. 修改前后作品有什么变化；
6. 哪一部分仍然不能完全相信。

最终评价看：

- 是否识别了 Agent 局限；
- 是否有可验证的个人贡献；
- 是否能区分生成内容和事实数据；
- 是否能解释工具调用；
- 是否完成验证而不是只看输出效果。

## 11. 与“智能仓管 Agent”方案的关系

“智能仓管 Agent”可以作为底层能力；“Agent 协作实验室”是上层教学软件。

```text
Agent 协作实验室
├── 项目目标与约束
├── Agent 对话与计划
├── 作品预览
├── 工具调用轨迹
├── 事实核验
└── 版本对比
        ↓
103 智能仓管 Agent
├── search_inventory
├── list_low_stock
├── get_item_location
├── get_safety_rules
└── InventoryService
```

这样第一节课展示的不只是“AI会查仓库”，而是完整的人机协作方法：

> 人定义目标，Agent拆解和生成，Java工具提供真实能力，人检查证据并做最终决定。

## 12. 建议结论

如果采用这个方向，第一周的主线应从：

> 做一个仓库查询程序。

升级为：

> 使用 Agent 协作实验室，共同制作一份 103 仓库数字导览；通过发现虚构内容、错误工具和缺失验证，学习怎样正确地与 Agent 协作，并修复一个真实的 Java 能力。

这能同时解决三个问题：

- 有视觉作品，课堂不枯燥；
- 能真实展示 Agent 的价值和局限；
- Java 基础不是被取消，而是变成支撑 Agent 正确工作的必要能力。
