# 第一周周日线下课优化方案：先让学生“入戏”，再完成第一个可运行版本

> 讨论稿 v0.1｜2026-10-16  
> 适用对象：3–4 名已接触 Java 基础语法、但尚未确认能独立完成“类 + 集合 + 输入处理”的学生。  
> 本稿仅优化第一周周日线下课，不直接替换现有《第一周教学大纲》。仓库项目与原“校园二手商品”主线存在方向变化，待教师确认后再统一全套文档。

## 1. 对现有构思的判断

“先看项目、再拆解实现”的方向是正确的，但当前方案有四个风险：

1. **时间写的是 90 分钟，实际 8:10–9:50 是 100 分钟。** 本稿按 8:10–9:40 的 90 分钟主课设计，9:40–9:50 作为可选答疑与环境处理。
2. **前 50 分钟主要由教师演示和讲解，学生第一次动手太晚。** 初学者容易从“觉得挺厉害”变成“这和我无关”。
3. **完整查询器同时要求类、List、搜索、筛选，与当前基础判断冲突。** 如果第一周直接要求这些，学生可能只能照抄，周汇报虽然好看，但无法解释或现场修改。
4. **观赏性不能只靠一张控制台表格。** 中文在不同终端和字体中的列宽可能不一致，复杂表格容易错位；真正吸引学生的是任务情境、即时反馈、故障挑战和自己的作品被投屏。

因此建议把课堂分成两层：

- **舞台层（教师展示）**：完整、好看、能搜索和预警，让学生知道最终会走到哪里。
- **学习层（学生实现）**：菜单、输入、分支、循环、固定数据展示和无效输入处理；通过诊断的学生再解锁 List 搜索。

一句话原则：**允许目标看起来很完整，但不要求学生第一周把完整系统抄出来。**

---

## 2. 课堂主线：103 仓库“早班异常任务”

不要以“今天学习变量、分支和循环”开场，而是直接给一个任务：

> 103 仓库马上要开放，但早班盘点发现一个物品位置不明、两个物品库存不足。你们需要先用系统查出问题；今天下课前，每个人都要让自己的第一版仓库程序跑起来。

课堂中始终围绕三个问题推进：

1. 系统怎样知道用户选择了什么？——输入。
2. 不同选择怎样执行不同功能？——分支。
3. 查完一次后怎样继续使用，直到主动退出？——循环。

术语在问题出现后再讲，不先连续讲概念。

---

## 3. 教师演示程序的观赏性设计

### 3.1 冷开场界面

教师进入教室后先投屏运行程序，不先讲背景和规则：

```text
========================================
          103 仓库 · 早班控制台
========================================
物品种类：9    低库存：2    待核对：1

[1] 查看库存
[2] 搜索物品
[3] 查看库存预警
[0] 退出系统
----------------------------------------
请输入操作：
```

让学生现场决定先按哪个选项。演示只走一条故事线：

1. 搜索“螺丝刀”；
2. 查看其位置；
3. 打开库存预警；
4. 输入一个错误选项，展示程序不会崩溃；
5. 退出。

整个冷开场控制在 3–4 分钟，不解释代码。

### 3.2 不建议把中文数据做成复杂宽表格

不同终端对中文、符号和 emoji 的宽度处理不完全一致。学生第一版可采用“物品卡片”，稳定且更容易阅读：

```text
[001] 螺丝刀
      类别：工具
      数量：25
      位置：A-01
      状态：正常
----------------------------------------
[003] 键盘
      类别：电子
      数量：2
      位置：C-03
      状态：! 低库存
```

教师演示版可以使用颜色，但学生作业不以颜色、动画、清屏或 emoji 为要求，避免把时间耗在终端兼容问题上。

### 3.3 用三个“舞台机关”增加吸引力

- **学生投票**：下一步查什么，由学生决定，不按固定讲稿点击。
- **故意制造一次错误**：输入 `9` 或空白，问学生“系统应该崩溃、退出，还是继续？”随后展示正确反馈。
- **前后对比**：先展示一段杂乱输出，再切换到分区、边框、状态标识清晰的版本，让学生说出哪个更容易使用。

观赏性来自“我参与了”“我猜中了”“我看到了变化”，不是来自教师连续展示更多页面。

## 4. 推荐的 90 分钟流程（8:10–9:40）

| 时间 | 环节 | 教师动作 | 学生动作 | 可见产出 |
|---|---|---|---|---|
| 8:10–8:14 | 冷开场 | 直接运行“103 仓库早班任务”，不讲代码 | 投票选择操作，观察系统反馈 | 知道课程最终要做什么 |
| 8:14–8:20 | 目标揭晓 | 展示完整系统的一条业务链；用一张图说明 Java 端与 C# 端分工，不展开架构细节 | 复述“用户做了什么、系统返回什么” | 建立最终项目图景 |
| 8:20–8:27 | 本周挑战 | 展示学生本周 V0，而不是完整教师版；明确必做和解锁任务 | 判断哪些功能自己已经会、哪些不会 | 每人领取任务卡 |
| 8:27–8:37 | 快速诊断 | 给 3 个微任务：改文字、补分支、让输出重复 3 次 | 每题独立尝试 2–3 分钟 | 教师确定学生起点 |
| 8:37–8:48 | 现场搭建一条纵切片 | 从空骨架完成“显示菜单 → 读取选择 → 执行一个分支”；边写边问预测，不粘贴完整答案 | 先预测下一行作用，再同步完成自己的版本 | 第一次成功运行 |
| 8:48–8:56 | 故障剧场 | 故意演示“一次操作后直接结束”或“无效输入后退出”的版本 | 找出行为和需求哪里不一致 | 从问题自然引出循环 |
| 8:56–9:08 | 第二次动手 | 只讲 while 和退出条件所需的最小内容；巡视时只给提示 | 让菜单至少运行两轮，输入 0 后退出 | V0 核心闭环 |
| 9:08–9:18 | 视觉改造挑战 | 给三张任选一张的改造卡，不统一照抄 | 独立选择并实现一项界面改造 | 作品开始有个人差异 |
| 9:18–9:27 | 微型作品展 | 随机投屏 2–3 份；每人只讲“我改了什么、怎么验证” | 30–45 秒演示或点评同伴一项优点 | 课堂高潮与即时成就感 |
| 9:27–9:34 | Agent 边界演示 | 对比“直接写完整程序”和“只给我排查步骤/解释概念”两种问法 | 把一个问题改写为只求提示的提问 | 会正确求助而非代写 |
| 9:34–9:40 | 任务发布与离场票 | 说明本周核心任务、解锁任务、验收方式 | 写下：已完成、最大卡点、回去第一步 | 教师得到课后分层依据 |

### 9:40–9:50 可选延长

仅用于：

- JDK、编辑器、中文编码或 Git 的个别环境问题；
- 未运行成功学生的一对一补救；
- 已完成学生展示解锁任务思路。

不要在这 10 分钟统一增加新知识，否则 90 分钟主课实际上又变回 100 分钟必修课。

## 5. 学生当天完成的 V0 应是什么

### 5.1 全员核心任务

每名学生下课时至少有一个能运行的程序：

```text
===== 103 仓库查询器 V0 =====
1. 查看今日示例
0. 退出
请选择：
```

必须具备：

- 能显示菜单；
- 能读取一行输入；
- 输入 `1` 显示教师给定的固定物品信息；
- 输入 `0` 正常退出；
- 输入其他内容给出提示并继续；
- 菜单能重复出现；
- 每人完成一项自己的文字或版式改造。

这已经能覆盖输入、分支、循环、退出和最基本的用户体验，不要求 Product 类或 List。

### 5.2 课堂视觉改造卡（三选一）

- **A 卡：界面分区**——加入标题、分隔线和清晰的输入提示。
- **B 卡：状态表达**——把固定物品显示为“正常 / ! 低库存”。
- **C 卡：引导文字**——无效输入时说明可用选项，退出时显示总结或再见信息。

要求学生解释自己为什么这样改，并用一次输入证明效果。

### 5.3 解锁任务，不作为全员硬要求

只有在快速诊断中能独立完成分支和循环的学生，才开放：

- 增加 2–3 条固定物品；
- 使用已学过的数组或 List 保存数据；
- 根据名称做一次简单搜索；
- 根据类别筛选。

如果学生没有学会类和集合，可以先用教师给出的只读数据或字符串数组，不为“项目看起来完整”提前塞入无法解释的 `Product` 类和 `ArrayList<Product>`。

## 6. 完整项目演示应如何压缩

原方案给最终项目 20 分钟，建议压缩到 6 分钟，只展示一条端到端故事：

1. C# 端发起一次查询或操作；
2. Java 端处理请求；
3. 返回仓库数据；
4. 界面展示结果或库存变化。

只回答三个问题：

- 用户在哪里操作？
- Java 端负责什么？
- 数据最后怎样被看见？

不要在第一节课讲控制器、服务、数据库、JSON、线程或部署。可以把这些模块遮住，告诉学生后续每学会一层就揭开一层。这样既保留“宏大目标”，又不会造成认知过载。

---

## 7. Agent 环节的更合适做法

第一周仍坚持：不让 Agent 生成要提交的完整业务代码。但课堂上最好现场演示一次“正确求助”，否则规则只有禁止，没有方法。

### 不合适

```text
帮我写一个完整的 Java 仓库查询系统，要有菜单、循环、搜索和 List。
```

### 合适

```text
我的菜单执行一次后就结束了。请不要写完整代码，只告诉我应该检查哪三个位置，并解释循环退出条件是什么。
```

或：

```text
请用生活例子解释 while 循环。不要给我本次仓库作业的代码。
```

学生在 `AI_LOG.md` 记录：原问题、自己试过什么、Agent 给了什么提示、最后怎样验证。第一周不要求为了填记录而强制使用 AI。

## 8. 周汇报不建议第一周强制录屏

如果只有 3–4 名学生，建议采用“现场 60–90 秒 + 可选录屏”：

1. 20 秒：我做的是 103 仓库查询器 V0；
2. 30 秒：运行 `1 → 无效输入 → 0`；
3. 20 秒：指出自己改的一处界面或规则；
4. 20 秒：说一个卡点和下周要增加的功能。

录屏会额外带来剪辑、声音、上传和隐私处理成本，容易让第一周评价偏向视频制作，而不是 Java 能力。需要留档时，教师统一录制现场展示或只收一张运行截图即可。

## 9. 教师课前必须准备的材料

1. **教师演示版**：完整查询、预警、错误输入处理；只演示，不发源码。
2. **学生启动骨架**：只含类入口、Scanner 调用示例和 TODO，不含完整分支与循环答案。
3. **一页项目地图**：C# 端、Java 端、数据三块即可。
4. **三张视觉改造卡**：A 界面分区、B 状态表达、C 引导文字。
5. **离场票**：已完成 / 最大卡点 / 回去第一步。
6. **离线备用包**：JDK 安装包或统一路径、编辑器配置说明、演示录屏或截图，避免网络或投影故障导致整节课失去主线。
7. **统一演示数据**：6–9 个虚构物品；避免真实个人、账号、资产或敏感仓库信息。

## 10. 对原方案的直接调整结论

保留：

- 第一节先展示最终项目；
- 第一周围绕一个可运行的小项目；
- 每周汇报以“我做了什么”为主；
- Agent 第一周只做概念、报错和思路提示。

调整：

- 最终项目演示从 20 分钟减到 6 分钟；
- 第一次学生动手提前到开课后 27 分钟，且之后每 10–12 分钟都有一次动作；
- “完整仓库查询器”从全员第一周任务改为教师舞台版或进阶解锁任务；
- 全员版本先完成菜单、固定数据、输入、分支、循环和退出；
- 用任务故事、故障剧场、视觉改造卡、微型作品展提升观赏性；
- 第一周不强制录屏，不用视频制作效果代替代码掌握；
- 根据 8:10–9:40 的 90 分钟执行，9:40–9:50 只作可选答疑。

## 11. 本轮待教师确认

1. 最终主线是否正式从“校园二手交易”切换为“103 仓库系统”？
2. 103 仓库系统中，Java 端与 C# 端的实际职责分别是什么？项目地图需要按真实架构绘制。
3. 周日固定课时是 8:10–9:40（90 分钟），还是 8:10–9:50（100 分钟）？
4. 学生目前是否已经在校内学过数组、类或 ArrayList？这决定解锁任务用数组还是 List。
5. 周汇报是否必须留视频材料？若不是，第一周建议现场短演示为主。
